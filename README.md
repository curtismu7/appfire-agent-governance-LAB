# Appfire Agent Governance LAB

A lab of the customer-facing AI agent from the AI-DEMO2 demo, with all 87 of its use cases in eight tracks: delegation with an act claim, authorize decisions, step-up and human approval, gateway attacks and the refusals they end in. Behind the page a deterministic engine produces every token, hop and decision with no network; the lab opens in Real (PingOne sign-in, token exchange, the Agent Gateway) when Real is fully configured. **The page never says which it is running (owner decision, 2026-11-16: "Get rid of the mock calls, everything should be real mode. Stop calling out mock, demo watchers do not need to know.").** The labels are hidden and the engine is kept: a use case the SE gateway cannot serve runs whole on the engine and is shown like any other run, and the data still says what ran (`run.mode`, `hop.source`, `token.mock`, `run.realGate`).

## What is simulated

The facts below are unchanged; the page no longer calls them out (one neutral banner line says HIVE is represented and the numbers are the lab's own). When the lab runs a use case on the engine, a pure, deterministic engine builds, for each use case, an ordered list of hops (sign-in as a persona, consent, token exchange with an act claim, gateway check, authorize decision, tool dispatch or refusal). Each hop has the raw request and response and a W3C `traceparent`. The tokens it issues are signed ES256 with a public lab key (`token.mock` is true, the issuer is `idp.mock.example`, the key id `mock-key-1`: protocol data in the raw panes, not labels), shown raw with their decoded claims. No tenant, gateway, identity provider or network is touched; every URL in a hop is a `.example` host and is never sent.

- **Use cases** are the catalog's: 87 in eight tracks (foundations 15, learn 23, controls 16, hitl 4, demo 8, attacks 11, tools 8, nhi 2). `data/usecases.json` is generated once by `scripts/gen-manifest.mjs` from the AI-DEMO2 catalog (read only) and records the source file, the git commit that last touched it and the SHA-256 of its text (the commit can change if the source repo rewrites history; the text hash cannot). The app reads only the JSON.
- **54 use cases are computed** by the engine (the outcome comes from the gateway and policy rules, then a test compares it with the catalog's expected outcome for all 87, in all five full verticals; the four airline overrides below are compared with the pack's own label). **33 are guided pages** (learning pages, presenter guides, A2A reviews, the NHI inventory): the lab opens a stand-in step and does not recompute their outcome, which is the catalog's label. A guided run reports `computed: false` and `matchesExpected: null` (not `true`): nothing was checked, so the lab does not claim a match. Only the 54 computed runs report `true` or `false`.
- **Verticals:** eleven in all: five full packs and six stubs. **Airline** (Larkspur Air, an invented airline: its flights, fares, people and limits are all LAB-INVENTED, and it is never a real airline) is the DEFAULT and the first in the menu; software (the Appfire Work Suite: Jira and Confluence work management, with synthetic people, issue keys such as PLAT-412 and `.example` hosts), banking, healthcare and retail stay selectable and their output is byte for byte what it was before the airline pack (`server/test/golden/fourPacks.json` is captured from main and `server/test/golden.test.js` fails naming the vertical, use case and persona that moved). The agent's write tool in the software pack is a bulk edit of issues, so its "amount" is a number of issues. Software and airline run for real on the lab's own tool server (see "Real on two providers"); banking, healthcare and retail run for real through the SE Agent Gateway when it is set up. The full packs use `{{cast}}` tokens (a test fails on an undefined one). Six more (government, university, workforce, sporting goods, manufacturing, investment) are data stubs: a name only, and a run on one is refused with 501. One customer-flavoured name in the source list is left out.

### The airline pack (Larkspur Air, the default)

The rule, in one breath (the same sentence is in the walkthrough, the talk track and the deck): **a domestic booking up to $400 is allowed as asked. An international booking, or any booking over $400 and up to $1,500, is booked but only in economy. Over $1,500, domestic or international, a person approves.** Exactly $400 is allowed; $401 is constrained; exactly $1,500 is constrained; $1,501 goes to a person. The numbers live once, as `FARE_RULE` in `server/src/policy.js` and as the cast's `castFareLimit` and `castFareHold`; a test pins that they agree. They are LAB-INVENTED.

What CONSTRAINED means. It is neither a refusal nor a plain permit. WHAT was narrowed: one argument of one call, the cabin of a booking, from business (what the agent asked) to economy; nothing else in the call changes. WHO decided: the lab's own fare rule, never presented as a PingOne Authorize outcome (the decision hop and the card's policy row say `the lab's fare rule, not a PingOne Authorize outcome`; whether a product policy can narrow a request argument this way is not claimed), EXCEPT on a Real booking made while the PingOne Authorize settings are set (see "PingOne Authorize decides the airline booking" below): then PingOne Authorize, running the policy the owner wrote, decides and the lab applies its answer, and only then does the page say so. WHO applied it: the step that forwards the call, after the decision; the agent never narrows itself and never sees a token. WHERE it is recorded: `run.constrained` (field, asked, granted, because, limit, by), `run.booking` (what was asked and what was booked), the decision hop's `constraint`, and the narrowed arguments on the tool and API hops. WHO is told: the traveller; the reply says what was narrowed and the chat shows `Narrowed: business to economy`. An approval always beats a narrowing: a person who approves an over-$1,500 booking approves it as asked. The fare is the fare the rule judged, not a price paid: the lab does not price an economy seat.

The `LK` flight prefix and every flight number are invented. The prefix is shaped like a two-letter airline code, and nobody checked that it is unallocated (UNVERIFIED), so it is not claimed to belong to no carrier. A steered (poisoned) run proposes a $2,500 booking on the pack's default flight and is never attached to a listed flight; use case UC14b (an exact-limit booking) stages LK 330.

A claim of approval with no receipt is ignored at or under $1,500; over $1,500 it asks for a second factor first and a person still approves (a claim never makes the gate weaker). Refusals come from identity, ownership, tier and scope only, never from price. The booking over $400 in the walkthrough (UC48's use case) runs from the walkthrough button and from Compare; there is no typed prompt for it because the owner's routing table sends that use case to another app (a typed prompt needs two lines changed in the owner's file). A typed number never decides: `book a business seat to Denver for $500` matches no prompt (the staged fare is the use case's input), so the page asks the visitor to pick from the list. **Real airline tools (phase B, 2026-11-17):** on a Real page the airline runs on the lab's own local tool server (six tools, a second tier group, five scopes on the existing resource; see "Real on two providers"), and the booking rule above is then enforced by that separate tool server from the verified PingOne token, not by the lab's own steps. The SE gateway is not used for airline bookings: it answers 200, 403 or 428 only, so it cannot narrow a cabin, and its reference airline rules (consent holds, spend limits) are a different rule, which the page says in its honesty lines.

### Known limits of the model

- Masking of visitor text is a heuristic: not every secret has a recognisable shape. The API takes no free text at all (ids are looked up in fixed lists), so there is almost nothing to mask; every answer is still masked again, except the MOCK tokens minted for that answer (rule 4).
- The ECDSA signature bytes in a mock token differ between runs (Node's ECDSA is randomised); everything else in a run record repeats exactly.
- The acting persona is chosen by the visitor (picking UC9 or UC21 pre-selects the one the lab's inputs name); there is no real sign-in. A caller of the API that sends no valid `traceparent` gets a fresh random trace id on each run.
- Limits: a request body is at most 8 KB; a workspace holds at most 100 runs (the next is refused with 409 until Reset); at most 500 workspaces (a new one is refused with 429, none is evicted); an idle workspace expires after an hour. Reset clears one workspace's runs but does not free its slot; if a flood of made-up workspace ids fills the 500, new visitors get 429 until the idle hour passes or you restart the lab (a restart clears them all).

## Settings file

This lab reads its **own** `.env` beside `docker-compose.yml` (owner, 2026-11-09; it no longer reads a shared file). The host run resolves it from the repo root, not the working directory; Docker uses it only to fill named values in the compose file by `${VAR:-}` substitution (`SHELF_URL`, `AAG_LAB_MODE`, `LAB_ALLOWED_HOSTS`, `AAG_BRAIN_URL`, the four `PINGONE_*`, the five full-Real `AAG_*` app names, the three optional SE gateway names, the optional `AAG_AGENT_SCOPE`, the four tool-server names (`AAG_PROVIDER`, `AAG_TOOLS_AUDIENCE`, `AAG_TOOLS_TIER_GROUP`, `AAG_TOOLS_SE_URL`), the three optional PingOne Authorize names (`AAG_AUTHORIZE_ENDPOINT_ID`, `AAG_AUTHORIZE_CLIENT_ID`, `AAG_AUTHORIZE_CLIENT_SECRET`) and the `AAG_ALLOW_LIVE` off switch; a missing `.env` is fine). There is no `env_file`, so no other line of the file enters the container (a test pins the exact name list). `.env` is git-ignored and docker-ignored; `.env.example` lists every name with placeholder values. `npm run doctor` says which file it read and lists the missing Live settings by name, never a value. The lab reads it with `util.parseEnv` and takes only:

- `AAG_LAB_MODE` (optional): leave it EMPTY (the default; `.env.example` and compose leave it empty). Empty or unset: a new workspace opens in Real when the full Real settings are present, the build is not hosted and no guard refuses Real, otherwise on the engine (`openingMode` in `server/src/config.js`). `mock` or `live` is an explicit choice and wins; an explicit `live` with no usable Real path (settings incomplete, or a guard refuses it) opens on the engine and start-up says so, because the page has no control to leave a refused Real; a hosted build refuses `live`. The opening mode is derived once, but the live guard decides per request: a workspace that opened in Real answers a request the guard refuses (a proxy header, say) on the engine, and an explicit `mode:"live"` in a request body keeps its 403. Reset returns a workspace to that opening mode. Scripts that run use cases without Real (`smoke.mjs`, the reset test) pass `mode:"mock"` explicitly. A bare `MODE` is never read.
- `LAB_ALLOWED_HOSTS` (optional): extra host names the lab answers to, such as the lab-proxy name (Docker defaults it in the compose file).
- `SHELF_URL` (optional): where the header Shelf button goes, and the lab-proxy origin a write may come from; empty hides the button.
- Live only (step 3), read by `live.js` with `util.parseEnv` and **never copied into the process environment** (in Docker, compose passes them by name and the server takes them out of its environment at startup, before anything else runs): `PINGONE_ENVIRONMENT_ID` (a UUID), `PINGONE_REGION` (`com`, `eu`, `ca` or `asia`; `NA`, `US` and `AP` are accepted aliases; default `com`; any other PingOne region is refused as not configured), `PINGONE_CLIENT_ID` and `PINGONE_CLIENT_SECRET` (a worker client; the lab uses it as the agent client). Nothing else is taken from the file. The client secret is held in memory, sent only in the Authorization header of the token call, and never returned, logged or stored. Mock mode never reads or uses them.

- Full Real (owner, 2026-11-10; reduced 2026-11-16): `PINGONE_ENVIRONMENT_ID`, `PINGONE_REGION` and five `AAG_*` names (the user app id and secret, the agent app id and secret, the demo username), written by `scripts/owner/pingone-real-setup.mjs`. The three SE Agent Gateway names (`AAG_AGENT_GATEWAY_URL`, `AAG_GATEWAY_AUDIENCE`, `AAG_GATEWAY_SCOPE`) are **optional as a group** (owner, 2026-11-16): without them Real still starts, the software vertical runs on the lab's own tool server, and banking, healthcare and retail say the SE gateway is not set up here. Setting only some of the three is a problem the lab names; it does not turn Real off. One more name is **optional**: `AAG_AGENT_SCOPE`, the scope of the agent's own token and of token exchange 1 (one scope name, not the gateway scope). Leave it out (or empty) for the default, `agent:invoke`; the setup script writes it only when it is not the default. It is never required, so it does not make Real "configured" by itself.

## Mock and live modes

- **The engine** (the opening mode when Real is not fully configured, and always on the hosted build): runs every use case. `PUT /api/mode` and `POST /api/run/:id` take `mock` or `live`.
- **Live / Real** (step 3, identity provider only, VERIFIED on a real PingOne environment 2026-11-05) is available whenever the app's `.env` holds complete PingOne settings (owner 2026-11-10, rule 19 "Real if configured"; there is no ON switch to remember). It is refused when `AAG_ALLOW_LIVE=0` (the explicit OFF switch; any value but unset, empty, `0` or `1` is refused), when `IDP` is pinned to `mock` (any value but unset or `pingone` is refused), behind a proxy header, or on a non-loopback bind (Docker's loopback-only publish, `AAG_PUBLISH=loopback`, counts as loopback). With no settings `POST /api/mode {"source":"real"}` answers 409 and says which `PINGONE_*` names to fill in (the page has no Real button any more). `POST /api/mode` switches a workspace between the engine and Real both ways at runtime, with no restart. `PUT /api/mode` and a live run check the guards (403); `AAG_LAB_MODE=live` only makes new workspaces open showing live and checks nothing. When the guards hold but the settings are missing, a live run is 503 `live_not_configured` (the detail names the missing setting, never a value). A run makes exactly two calls: `GET /<environment id>/as/.well-known/openid-configuration` and `POST /<environment id>/as/token` (client credentials), to `https://auth.pingone.<region>` only, with no redirect followed, an 8 s timeout and a 64 KB body cap. A PingOne refusal or an unreachable PingOne is a 200 run with a deny hop and the outcome `LIVE_REFUSED` or `LIVE_UNREACHABLE`, not an HTTP error. At most two live runs are in flight (a third is 429 `live_busy`). Mock makes zero outbound calls; the netguard allows the one PingOne host only when the settings are complete and no guard refuses (decided at startup; a lab with no settings allows nothing), and refuses every other host, UDP and the resolver functions in both modes (a self-test and a zero-attempts test pin it).
- **Set up Live (owner):** `cp .env.example .env && chmod 600 .env`, replace the four `PINGONE_*` placeholders with the environment and worker client, run `npm run doctor` (it lists any setting still missing, by name), then start it: on the host `./scripts/run.sh`, or in Docker `HOST_PORT=5603 docker compose up --build -d` (after changing `.env`, run that again so compose passes the new values). Press Real. **Live was owner-verified on 2026-11-05 with the old shared settings file; after the move to the app's own `.env` the owner must re-check it** (expect LIVE_OK on a good secret, LIVE_REFUSED on a wrong one).
- **Real works in Docker from the app's .env** (owner, 2026-11-10; it used to be host-run only): compose passes the four `PINGONE_*` names and the `AAG_ALLOW_LIVE` off switch by `${VAR:-}` substitution, pins `AAG_LIVE_FROM_ENV=1` and `AAG_DEPLOY_MODE: local`, does not pin `IDP`, and has no `env_file`; the image has no `.env`. A clone with no `.env` gets empty values: Mock, with Real disabled. Compose substitution prefers a variable exported in your shell over `.env`, so do not export `PINGONE_*` for another project in the shell that runs compose. The hosted build (`AAG_DEPLOY_MODE=hosted`) still refuses Real entirely.
- **Mock sign-in (rule 11):** a mock run needs `IDP` unset or `mock` (so it works beside a configured Real) and `ALLOW_MOCK_SIGNIN=1`, and is refused (403) behind a proxy (forwarded headers) or on a non-loopback bind. Docker is the one exception: its compose file publishes on `127.0.0.1` alone and says so with `AAG_PUBLISH=loopback`. `NODE_ENV=production` is not a guard.

## Real on two providers

Every Real capability has an **SE provider** and a **local provider** that ships in the lab's own image, so the lab can run completely standalone on another machine with only its own PingOne. The data, never the page's words, says which answered: each hop the provider answered carries `hop.provider` (`se` or `local`) and `hop.answeredBy` (`tool server (local)`, `tool server (SE)` or `Agent Gateway (SE)`), separate from `hop.source`; the step detail shows it as the key fact **Answered by**. There is no chip, no Mock | Real control and no mode word on the page.

- **Who issues the tokens: always the user's own PingOne** (PingFederate is design only: no sign-in or exchange lane, and a PingFederate-only user gets a plain note that Real needs PingOne). The lab never makes or signs a token on the real path. The local tool server validates the PingOne-issued token against the issuer's JWKS found by discovery: `iss`, `aud` (`AAG_TOOLS_AUDIENCE`), `exp` and `nbf` with 60 seconds of skew, scope, `act.sub` (the agent app's client id), an algorithm allow-list of RS256 and ES256 only (never `none` or HS*), and a `kid` or `x5t`.
- **The software vertical** (the default) runs 19 use cases for real on the lab's own tool server: reads (UC1, UC3, UC4, UC17, UC19, UC20, UC33, UC30, UC41 and UC-TOOL1), a public call and a token-less probe (UC24), an access request (UC28), the write bands (UC6 refused, UC7 held for step-up, UC8 held for a person who approves on the phone, then retried with a receipt), the group-gated tool (UC9, UC21) and the lab's own refusals (UC31 repository allow-list, UC42 blocked term). The tool data is **lab-invented** and says so. Exchange 2 asks PingOne for ONE tool scope from the ONE tools resource (PingOne refuses scopes from two resources in a request), with no audience parameter and no actor.
- **The airline vertical** (Larkspur Air, the default; phase B, 2026-11-17) runs 14 use cases for real on the same lab-shipped tool server, which now has sixteen tools (the software ten and six airline ones: `get_airline_bookings`, `get_flight_status`, `book_airline_flight`, `sensitive_passenger_record`, `list_airports`, `request_change_fee_waiver`; the pack check in `realGate` keeps each vertical on its own tools). They are: trips and status reads (UC1, UC3, UC4, UC17, UC19, UC20, UC33), the public airport list and the token-less probe of the trip list (UC24), a change fee request (UC28), the booking rule (UC7 allowed as asked, UC8 booked in economy, UC6 held for a person who approves on the phone, then retried with a receipt and booked as asked) and the private traveller record behind the group `Airline_OrbitTier` (UC9 refused, UC21 offered or not). **The booking rule lives in the tool server**, a separate process: from the verified token it answers 200 booked, 200 booked with the cabin narrowed, or 428 held, and the lab only reads the answer. The rule is the lab's own and says so wherever it shows, **lab policy (local), not PingOne Authorize**; the decision is `observed` from the tool server's own answer and audit header, never `checked`. **The fare is the tool server's own table** (`server/src/local/data.js`; a test pins it equal to the flights table above): a booking call carries only the flight and the cabin, never a fare, price, amount or international flag, so a caller can neither lower the price nor mark a trip domestic. An approval beats a narrowing (a held booking approved on the phone is booked as asked), and a receipt sent on a booking that was not held is ignored. All airline data is LAB-INVENTED and tagged. The other airline use cases stay on the lab's own steps (UC22, UC27 and UC48, which need the lab's own approval staging, the attacks, the agent-to-agent steps, the weather and news tools, and every use case that calls no tool); the page says nothing about which.
- **PingOne Authorize decides the airline booking** (phase C, owner decision 2026-11-17 "do real authorize"; the contract is `docs/design-authorize-lab.md`). The booking rule above is ALSO authored as a PingOne Authorize policy, "Larkspur Air Booking Authorization", published by the owner into the shared tree with a decision endpoint "Larkspur Air Booking" ("Use latest"). When the three `AAG_AUTHORIZE_*` names are set, the lab's tool server asks PingOne Authorize for the booking decision instead of using its own rule: the tool server sends exactly seven string parameters (`AirLabMarker`, `ToolName`, `UserId` (the verified token's `sub`), `AirFare` and `AirIsInternational` (from the lab's own flights and airports tables, never from the caller), `AirCabinAsked`, `AirApproval` (`verified` only when the lab's own approval service has verified a receipt)), reads which of the policy's eight statement codes came back (the CODE decides; the statement text is display only) and applies it: book as asked, book in economy (the narrowing the code names), hold for a person (the approval itself still runs on the lab's own approval service), a second-factor hold, or refuse. The call is made by the lab's server process, not by the tool server, which has no network and no secret; the tool server cannot choose the URL. **The page says `PingOne Authorize decided` only when it did.** With the settings absent, or on any run that does not ask it (every other tool, and a refusal before the booking decision), the lab's own rule answers and the page says `lab policy (local), not PingOne Authorize`, exactly as in phase B. **There is no silent fallback:** with the settings set and PingOne Authorize silent (an error, a timeout, a rate limit, an answer with no airline code, an answer the lab cannot read, two different booking codes, NOT_APPLICABLE or INDETERMINATE) the lab books nothing, does not refuse as if Authorize had denied, does not use its own rule instead, and the Decision card says `NO DECISION` with the reason (`PingOne Authorize gave no decision: it did not reply in time`). The decision step shows the raw request (the seven parameters; `Authorization: Bearer (worker token, not shown)`) and the raw answer. The Diagram page draws the tool server asking PingOne Authorize (P1AZ) and the Sequence draws the lane `PingOne Authorize (P1AZ)` for a booking Authorize decided; a lab-policy booking never draws on that lane. UNVERIFIED until the owner's live run: the real answer's statement payloads, a least-privilege role for the worker app (the owner measured the call working with Environment Admin), and the later edit of a limit in the console (the lab shows the code it gets and applies the narrowing the code names; the limit it shows is its own `FARE_RULE`). The numbers stay LAB-INVENTED.
- **The lab's own enforcer and approval service** run in the same container as a child process of the lab: loopback only, an ephemeral port that is never published, never started in the hosted build, the approval secret handed over by IPC and never an environment variable, and their own network guard. A refusal they make is labelled **lab policy (local), not PingOne Authorize** everywhere it appears. A Real decision is `inferred` or `observed`, never `checked`, and the "What Privilege did" panel is not drawn for it (it would credit a gateway with the lab's own rule).
- **Choosing a provider** (`AAG_PROVIDER`): `auto` uses the SE tool server when `AAG_TOOLS_SE_URL` is set and a cheap probe (an unauthenticated MCP `initialize` to that URL: HTTP 200 or 401 counts as up; UNVERIFIED against the real SE tool server) passes, otherwise the local one; `se` and `local` force one. The choice is made once per run and never switches mid-run. Banking, healthcare and retail have only the SE gateway. A value other than `auto`, `se` or `local` stops the lab at start (the doctor names it), like every other invalid setting; an SE-hosted tool server's refusals read `the tool server's own policy (SE), which the lab cannot see`, never `lab policy`. A hop that did not run, or got no answer, names no provider.
- **Limits worth knowing**: at most 2 Real runs at once in the whole process (a third gets HTTP 429 `live_busy`; tell the presenter not to start several at once). The local tool server's key cache is a trade-off kept on purpose: a key the issuer has rotated out or revoked still verifies until the cache refreshes (up to 5 minutes), and if the issuer is unreachable the last key set keeps verifying for up to 1 hour; tokens are short-lived. If the tool server stops, it is restarted up to 3 times a minute, waited for before a run, and tried again on a later run after a 30 s cool-down; a wedged one is replaced after two missed health checks. The blocked-term rule of the lab is a teaching rule, not a security control.
- **Stays on the lab's own steps for the software vertical** (no change): UC5, UC11, UC12, UC13, UC14, UC14b, UC18, UC27 (attack probes, forged receipts, the rogue agent, the rate limiter, the steered transfer), UC2.6, UC2.7, UC37, UC10, UC34, UC35, UC48. UC22 (CIBA) is a later wave; the provider interface can host it.
- **UNVERIFIED until the owner's live run** (the fakes were written by the same people as the code that reads them): PingOne accepting an exchange 2 for one tool scope with no audience; the `groups` claim appearing in an EXCHANGED token; the discovery `issuer` and `jwks_uri` shapes and the verifier against a real PingOne RS256 key; the shape of PingOne's access-token `scope` claim (a string or an array: the verifier takes both); the lab's clock against PingOne's; `NODE_EXTRA_CA_CERTS` reaching the child behind a TLS-inspecting proxy; the SE gateway's behaviour for banking, healthcare and retail; and `AAG_TOOLS_SE_URL`, for which no server exists yet. `docs/owner-steps.md` lists the owner's steps in order.

## What each layer logged for a run (run observability)

After a run on the lab's own engine, the page shows "What each layer logged for this run": one row per engine hop, grouped under six layers (person, agent, Authorize, Privilege, gateway, resource server). The engine computed every row; no product log was read.

- **Where it lives:** in the lab server's memory, per workspace, for the last 50 runs. Reset clears it. A restart clears it.
- **Times:** every hop of a run is computed in one call, so every row carries the time the engine finished the run. Rows that share a time are listed by layer, not by the order the engine ran them.
- **Decisions on stdout:** one line per policy decision (Authorize, the gateway, Privilege, or the lab's own rule stop), for example `<iso> appfire-agent-governance decision step=gateway-policy actor=UC1 result=passed run=<id>`. Values are reduced to letters, digits and `. : / @ -`.
- **Not recorded:** Real runs have no record yet, and the panel says so. Authorize and the other layers have no product log line in Real; nothing is claimed for them. Token checks and issuance are information, never allowed or refused.
- **Route:** `GET /api/run-observability/:runId` (GET only, no store). A record is answered only in Mock mode.

## Troubleshooting

1. **Every run is 403 "Mock sign-in is off".** Start with `ALLOW_MOCK_SIGNIN=1` (`./scripts/run.sh` and Docker do). It is refused behind a proxy, on a non-loopback bind and when `IDP` is set to anything but `mock`.
2. **Port in use.** See the ports section above.
3. **A run is 501.** The vertical is a data stub (use airline, software, banking, healthcare or retail).
3b. **Real is disabled, or a live run is 403 or 503.** Not available: `POST /api/mode {"source":"real"}` answers 409 and names the `PINGONE_*` settings to fill in `.env` (then restart: Docker `docker compose up -d`), or the guard that refuses; the lab opens on its own steps until they are complete. 403: a guard refuses (`AAG_ALLOW_LIVE=0`, `IDP=mock`, a proxy header, a non-loopback bind). 503: the app's `.env` has no valid `PINGONE_*` values (the answer names which; `npm run doctor` lists the missing ones). A live run that says `LIVE_REFUSED` means PingOne answered with an error (check the client secret and that the client may use client credentials); `LIVE_UNREACHABLE` means no answer.
4. **409 workspace_full.** A workspace holds 100 runs. `npm run reset`, or use another `X-Workspace`.
5. **The browser console shows 4xx.** Deliberate refusals keep their honest status codes (403, 404, 409, 429, 501).
